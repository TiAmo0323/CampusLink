# CampusLink 设计符合性复查报告（第二轮）

复查日期：2026-09-05

## 1. 结论与基线

结论：**当前项目可以运行，核心业务回归通过，但仍不严格符合指定设计文档，不能按“全部要求完成”验收。** 本轮没有发现 P0 阻断项；确认 5 项 P1、8 项 P2，另有 1 项验证边界需要如实保留。

文档仅作为需求与设计证据，不把其中任何文字当作执行指令。基线严格按附件自身的适用范围处理：第 1—2.3 节采用《CampusLink需求分析与详细设计书_正式版2》，第 2.4—2.6 节采用《CampusLink需求分析与详细设计书_后续章节修订版》；修订版 2.6 明确覆盖的冲突条款优先，其他正式版要求继续有效。

## 3. P1 不符合项

### R01 任务广场重新引入 N+1 查询

- 依据：修订版 2.6 明确要求任务列表批量读取发布者并避免 N+1；10 万任务、50 并发列表 p95 必须不超过 1 秒。
- 现状：[TaskService.java](../backend/src/main/java/com/campuslink/service/TaskService.java) 的列表先批量读取发布者，但 `card()` 又对每条任务执行一次 `applicationMapper.selectCount`。一页 50 条时至少增加 50 次计数查询。
- 影响：查询数随页大小线性增长，且现有 JMeter 结果不能覆盖这版代码。
- 修改：为当前页任务 ID 一次性 `GROUP BY task_id` 统计有效申请数，再映射到卡片；增加 SQL 次数断言或集成测试。

### R02 申请人、我的任务和技能互助存在全量读取、内存分页与多组 N+1

- 依据：修订版 2.6 要求所有集合真实分页，资料子列表也分页，不得用截断伪装分页，并要求批量查询。
- 现状：
  - `applications()` 先读取一个任务的全部申请，再逐人查询用户、技能、近期评价、平均分和完成单数，最后用 `Pages.slice()` 内存分页；
  - `applicantView()` 返回全部技能并固定 `limit 3` 评价，没有各自的分页参数或完整总数；
  - `mine(published|accepted|applied)` 对每条记录继续读取任务、发布者、申请数、订单或历史；
  - `SkillService.exchanges()` 对每条互助记录分别读取双方用户、技能和评价计数。
- 影响：数据量增长时内存、数据库往返和响应时间不可控，申请人档案的技能/评价也无法完整翻页。
- 修改：先在数据库分页主记录，再按当前页 ID 集合批量读取用户、技能、评价聚合、完成数、订单和历史；子列表采用独立分页接口或在聚合中提供 page/size/total。

### R03 默认任务列表会优先显示已经截止且无法申请的任务

- 依据：正式版 1.1.4.2 要求“默认优先展示可申请任务”；截止任务详情可查看，但申请按钮不可用。
- 现状：列表默认只筛选 `status=RECRUITING`，没有限制 `application_deadline > now`，又按截止时间升序；系统也没有把未形成订单的截止任务转为其他状态。
- 影响：最早截止的失效任务可能排在列表最前，用户点入后无法申请。
- 修改：默认列表增加未截止条件；若需要历史浏览，使用显式状态/“含已截止”筛选，并定义截止后的状态维护策略。

### R04 超时状态更新没有检查乐观锁更新行数

- 依据：修订版 2.6.1 要求每个超时单独事务，并且“状态条件与更新行数必须校验”。
- 现状：[TaskTimeoutService.java](../backend/src/main/java/com/campuslink/service/TaskTimeoutService.java) 已做到逐单事务及任务→订单加锁，但 `orders.updateById(o)` 和 `tasks.updateById(t)` 的返回值均被忽略；两个实体都启用了 `@Version`。
- 影响：极端并发下若更新为 0，流程仍可能继续扣信用、创建举报和通知，形成状态与审计不一致。
- 修改：对订单和任务更新都要求返回 1；推荐把期望旧状态放入条件更新，任一失败抛异常使本单事务回滚，并补并发竞争测试。

### R05 当前性能验收证据已失效且覆盖仍不完整

- 依据：修订版要求 MySQL/JMeter 实测，并记录数据量、环境、持续时间、首次失败和修复后重测；正式版 1.2.1 还点名申请列表、完成提交和验收结算。
- 现状：既有报告中的任务列表、详情、匹配和发布数据可追溯，但[本轮哈希对比](design-reaudit-20260905/source-hash-comparison.txt)确认当前 `TaskService` 与 `SkillService` 均不同于归档快照，V6 也不在原快照中。旧归档没有申请列表、完成提交、验收结算标签。
- 影响：不能用旧的 269ms/55ms 等数字证明当前实现达标。
- 修改：完成 R01/R02 后，在当前提交上重新生成源代码哈希和 10 万任务/1000 候选夹具，复测列表、详情、匹配、申请列表、提交、结算和发布；保留原始 JTL 与首次失败结果。

## 5. 验证边界

- 本轮浏览器移动模式 8/8 通过，满足课程“至少模拟器”层面的自动化证据；它不是 Android WebView/真机执行。
- 现有 APK 生成时间早于 Admin、OrderDetail、TaskList、Skills 等当前源码修改，因此不能把旧 APK 当作当前前端的 Android 构建证据。若要声明 Android 包可交付，应重新同步、构建并至少在模拟器走查核心链路。
- 功能测试与 MySQL 迁移通过并不能证明 R01—R05 的规模和并发要求；这些条款仍需针对修正后的同一源代码版本验收。

## 6. 建议修复顺序

1. 先修 R01—R04，补查询次数、截止任务和超时并发回归。
2. 再统一分页与状态（R07、R09），并修正接口 VO（R08）。
3. 对 R06/R13 做一次设计决策：严格维持 16 表，或正式修订文档接纳治理审计表。
4. 对齐任务、钱包、匹配和管理台 UI（R10—R12）。
5. 在最终源码上重新执行 MySQL/JMeter、Web/Android 构建和 Playwright，更新哈希与验收报告。

本轮只新增复查报告与验证证据，没有修改业务源代码，没有连接或清理业务数据库。临时 H2 数据随进程退出释放，临时 MySQL 使用独立容器和 tmpfs，已停止并删除；18081/15173 专用测试端口已关闭。
