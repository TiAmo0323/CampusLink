## JMeter实测

环境：Windows开发机，i7-14650HX（24逻辑处理器），约16GB内存；Java21、MySQL8 Docker临时库（数据目录tmpfs）、JMeter5.6.3；全部请求走127.0.0.1。MySQL与应用同机，这不是生产容量承诺。

初始100,003条任务，其中100,000条为只读压测夹具；新增1000名候选用户，实际匹配还包含演示候选。重测时已有约10.34万任务。夹具中的冻结余额用于读性能场景，不宣称为完整业务账本；真实压测发布均通过业务接口。

线程组顺序：50并发读60秒（10秒爬升），10并发匹配30秒，10并发同账户发布30秒。浏览器回归部分时间与重测重叠。持续时间共120秒；p95按所有样本近邻秩计算，成功率按HTTP200断言计算。

| 请求 | 重测样本数 | 成功率 | p95 | 本轮门槛 |
|---|---:|---:|---:|---|
| 任务列表 | 9,708 | 100% | 269ms | ≤1000ms |
| 任务详情 | 9,682 | 100% | 200ms | ≤1000ms |
| 千人候选匹配 | 5,816 | 100% | 55ms | ≤1000ms |
| 并发任务发布 | 2,453 | 100% | 175ms | ≤2000ms |

总计27,659请求，0失败。初次写入压测4,709请求中1,265失败，原因为先插入任务持有用户外键共享锁、再冻结积分升级用户行锁而死锁；修正为发布前先锁用户，再插入/冻结。首次与重测原始结果均保留，不能将首次结果算作通过。随后结算改用锁定查询返回的当前余额，另经MySQL双订单并发验证。

原始JTL/夹具计数归档：`docs/verification/jmeter-20260905.zip`。原始本机结果：`backend/target/performance/`（该目录可能被mvn clean清理）。

## 复现与升级注意

后端普通回归不需要Redis：
```powershell
mvn.cmd -f backend/pom.xml test
npm.cmd --prefix frontend run build
docker compose --env-file .env.example config --quiet
```

浏览器测试必须连接**隔离测试库**：用MySQL测试实例在18081端口启动后端，设置VITE_API_BASE=http://127.0.0.1:18081并在15173端口启动Vite，然后在frontend执行 `npx.cmd playwright test`。测试会创建账户、任务和流水，不能指向生产库。

性能夹具脚本只指向临时容器 `campuslink-revision-mysql-20260905` 和数据库 `campuslink_revision`；不要改成业务库。JMeter下载包放在backend/target后执行prepare_performance.py生成计划；重复压测可复用计划但令牌过期需重新生成。计划包含临时访问令牌，不应提交仓库。

升级需要前后端同时部署，旧访问令牌格式不兼容，应重新登录。已有MySQL库只应用V5，不删库、不改V1—V4；旧冻结流水未知值为NULL。默认H2是内存库，正式保存数据请使用MySQL并备份。生产环境关闭演示账号并替换默认密钥。本轮没有执行Git提交或推送。
